# Огляд репозиторію, встановлення та порядок запуску

Використано [arXiv Dataset](https://www.kaggle.com/datasets/Cornell-University/arxiv/data) (Cornell University, Kaggle): метадані наукових статей arXiv у форматі JSON Lines (один запис на рядок). Повний файл `arxiv-metadata-oai-snapshot.json` містить кілька мільйонів статей, тому для роботи береться підвибірка з перших **10 000** записів, у яких непорожні заголовок і анотація.

Після підготовки (`01_prepare_data.py`) кожен запис має поля:

| Поле | Опис |
|---|---|
| `id` | ідентифікатор статті на arXiv |
| `title` | заголовок |
| `abstract` | анотація |
| `authors` | автори (до 10, формат «Прізвище І.») |
| `year` | рік першої версії статті |
| `category` | основна категорія arXiv (перша зі списку) |

Підвибірка зберігається у `data/arxiv_subset.parquet`.

## Структура репозиторію

```

├── .gitignore

│   ├── 03_load_to_pinecone.py
│   ├── 04_search.py

└── README.md
```

## Порядок запуску

1. Перейти в директорію репозиторію:

   ```bash
   cd <назва-репозиторію>
   ```

2. Встановити залежності:

   ```bash
   pip install -r requirements.txt
   ```

3. Завантажити датасет із Kaggle (потрібен налаштований [Kaggle API](https://www.kaggle.com/docs/api) токен) і розпакувати його в корінь репозиторію:

   ```bash
   kaggle datasets download -d Cornell-University/arxiv
   unzip arxiv.zip
   ```

   Після цього в корені має з'явитися файл `arxiv-metadata-oai-snapshot.json`.

4. Створити файл `.env` у корені з ключем Pinecone:

   ```
   PINECONE_API_KEY=your_api_key_here
   ```

5. Запускати скрипти **з кореня репозиторію** (шляхи у скриптах відносні) і строго за порядком:

   ```bash
   python scripts/01_prepare_data.py       # підготовка підвибірки → data/arxiv_subset.parquet
   python scripts/02_embed.py              # ембеддинги → embeddings/embeddings.npy
   python scripts/03_load_to_pinecone.py   # створення індексу arxiv-papers і завантаження векторів
   python scripts/04_search.py             # семантичний пошук, фільтри, порівняння метрик
   python scripts/05_chunking.py           # чанкінг і пошук по чанках
   ```

   Скрипти залежать від результатів попередніх: `02` потребує файлу з `01`, `03` і `04` потребують ембеддингів із `02`, а `04` ще й завантаженого індексу з `03`.


# Відповіді на запитання

## Підготовка даних і вибір інструментів

1. **Pinecone, Qdrant і Chroma: розгортання, ліцензія, продуктивність**

Pinecone є повністю керованим хмарним сервісом із закритим вихідним кодом і пропрієтарною ліцензією. Його не можна розгорнути на власному сервері: інфраструктуру, масштабування, реплікацію та оновлення бере на себе провайдер, а користувач працює через API і платить за використання.

Qdrant і Chroma мають відкритий код під ліцензією Apache 2.0. Qdrant, написаний на Rust, можна запустити в Docker або Kubernetes у власній інфраструктурі, а також використовувати як керований Qdrant Cloud. Chroma орієнтована на простоту: її можна запустити вбудовано в Python-процес, як окремий сервер або в хмарі. 

З погляду продуктивності Pinecone та Qdrant розраховані на великі обсяги даних і виробниче навантаження (мільйони й мільярди векторів, фільтрація за метаданими, горизонтальне масштабування). Chroma найзручніша для невеликих і середніх колекцій та швидкого прототипування. Конкретні показники затримки й пропускної здатності сильно залежать від індексу, обсягу даних, розмірності та заліза, тому порівнювати їх варто на власному датасеті, а не за загальними цифрами.

Pinecone підходить, коли потрібен продакшен без операційних витрат на інфраструктуру, а команда готова до vendor lock-in. Qdrant підходить, коли потрібен повний контроль над даними, гнучка фільтрація та передбачувана вартість на великих обсягах. Chroma підходить для локальної розробки, прототипів, навчальних проєктів і невеликих RAG-застосунків, де важлива мінімальна кількість налаштувань.

2. **Чому specter2_base, а не all-MiniLM-L6-v2**

all-MiniLM-L6-v2 є універсальною моделлю, навченою на широкому наборі пар речень із різних джерел (форуми, питання-відповіді, загальні тексти). Вона добре розуміє загальну семантичну близькість, але не знає специфіки наукових публікацій. SPECTER2, за описом на HuggingFace, є “capable of generating task specific embeddings for scientific tasks when paired with adapters”. Картка пояснює, що на вхід моделі подаються заголовок і анотація наукової статті або короткий текстовий запит. Базовий енкодер навчався на понад 6 млн триплетів на основі цитувань наукових статей, тобто «схожими» вважаються статті, що цитують одна одну. Далі через адаптери модель донавчається на задачах SciRepEval у чотирьох форматах: класифікація, регресія, proximity (пошук найближчих сусідів) та adhoc search. Для пошуку за анотаціями arXiv це дає більш релевантну близькість, ніж загальна модель, яка бачить лише лексичну й тематичну схожість.

3. **Рекомендована метрика схожості**

У картці моделі specter2_base явної рекомендації щодо метрики схожості немає: вона описує вхідні дані та приклад отримання ембеддингів, але не називає метрику для індексу. Водночас у науковій літературі, що використовує SPECTER2, близькість документів зазвичай вимірюють за косинусною подібністю, і вона є природним вибором для моделей на базі BERT, навчених контрастивним методом на триплетах. Для індексу це важливо з двох причин. По-перше, метрика в Pinecone задається під час створення індексу й потім не змінюється, тож помилковий вибір вимагає створення нового індексу та повторного завантаження всіх векторів. 

По-друге, метрика визначає, що саме означає «схожий»: косинусна подібність порівнює лише напрямок векторів, а скалярний добуток і евклідова відстань залежать ще й від норми. Вектори SPECTER2 не нормалізуються автоматично, тому для dot product різниця в нормах могла б спотворити ранжування. 

## Чому для нормалізованих ембеддингів cosine similarity еквівалентна dot product

Косинусна схожість визначається формулою:

$$
\cos(a, b) = \frac{a \cdot b}{\lVert a \rVert \cdot \lVert b \rVert}
$$

Тобто це скалярний добуток, поділений на добуток довжин (L2-норм) векторів.

Якщо ембеддинги нормалізовані, то $\lVert a \rVert = \lVert b \rVert = 1$, і знаменник дорівнює 1:

$$
\cos(a, b) = a \cdot b
$$

Отже, обидві метрики дають однакові значення і однаковий порядок ранжування.

**Практичне значення:** скалярний добуток обчислюється швидше, бо не потрібно щоразу рахувати норми. Крім того, при нормалізованих векторах метрики `cosine` і `dotproduct` в індексі Pinecone дадуть однаковий результат.


## Частина 3 — Пошукові запити

### 1. Чи збігаються топ-5 для Cosine і Dot Product і чому?
**Так, результати топ-5 збігаються абсолютно.** 
Це відбувається тому, що під час генерації запиту було використано параметр `normalize_embeddings=True`, а локальні ембеддинги у файлі `embeddings.npy` також заздалегідь нормалізовані. 
* Оскільки вектори нормалізовані, їхні L2-норми дорівнюють одиниці ($\|A\| = 1$, $\|B\| = 1$). 
* Знаменник перетворюється на $1 \cdot 1 = 1$, відповідно формули стають тотожними: $Cosine(A, B) = A \cdot B = Dot\ Product(A, B)$.

### 2. Чи відрізняються результати для L2 і чому?
**Ні, склад і порядок статей у топ-5 для L2-відстані є абсолютно ідентичними до Cosine та Dot Product.**
Для нормалізованих векторів Евклідова відстань ($L2$) має пряму монотонну математичну залежність від скалярного добутку: 
* Чим **більшим** є значення косинусної подібності, тим **меншим** стає значення L2-відстані. 
* Оскільки залежність суворо монотонна, операція пошуку максимумів для Cosine та мінімумів для L2 повертає однакові індекси у тому самому порядку.

### 3. Що сталося б, якби ембеддинги не були нормалізовані?
Якби нормалізація була відсутня, **результати всіх трьох метрик кардинально розійшлися б**:
* **Dot Product** почав би сильно максимізувати вектори з великою довжиною. На практиці це означає, що статті з довшими текстами або специфічною частотою слів отримували б аномально високий скор, навіть якщо вони не релевантні за змістом.
* **L2-distance** натомість став би чутливим до абсолютних значень координат. Він міг би видавати меншу відстань до коротких або слабко виражених векторів просто тому, що вони географічно ближчі до початку координат ($0,0\dots0$), а не до змісту запиту.
* **Cosine Similarity** залишався б єдиною метрикою, яка адекватно оцінює семантичну схожість, оскільки формула косинуса автоматично ділить результат на довжину векторів, нівелюючи вплив розміру тексту.

## Частина 4 — Chunking

1. **Яка стратегія дає більш осмислені чанки?**

Більш осмислені чанки дає semantic chunking. Він об'єднує цілі речення, доки не буде досягнуто ліміту слів, тому кожен чанк починається з початку думки і закінчується її завершенням. Fixed-size chunking ділить текст суто за кількістю слів і не знає про структуру тексту, тож межі чанків випадково потрапляють у середину речення чи навіть термінологічної фрази. Ціна semantic-підходу полягає в нерівномірній довжині чанків (у нашому запуску середня довжина становила 45 слів проти 57 для fixed) і в залежності від якості розбиття на речення: простий регулярний вираз може помилково розрізати текст після скорочень на кшталт «e.g.» або «et al.». Якщо ж одне речення довше за ліміт, воно залишається цілим чанком і перевищує його. Fixed-size виграє передбачуваністю: розмір чанків і їх кількість легко оцінити заздалегідь.

2. **Чи є випадки розрізаних речень і як це впливає на ембеддинги?**

Так, у fixed-size стратегії такі випадки трапляються майже в кожній анотації: межа чанка збігається з межею речення лише випадково. У semantic-стратегії речення не розрізаються, тому цей ефект там відсутній. Для ембеддингів це має наслідки. Чанк, що починається посеред речення, часто втрачає підмет або контекст, а чанк, що обривається на півслові за змістом, містить незавершену думку. Модель кодує те, що бачить, тому вектор такого чанка відображає фрагмент, а не повну ідею, і відповідні запити можуть знаходити його гірше або, навпаки, помилково. Це особливо відчутно для specter2_base, яка навчена на зв'язних заголовках і анотаціях наукових статей, а не на довільних обрізках тексту. Перекриття (overlap) частково компенсує проблему, бо обірвана думка повторюється на початку наступного чанка, але не усуває її повністю.

3. **Як розмір overlap впливає на кількість чанків і покриття тексту?**

Для тексту з W слів, розміру чанка C та перекриття O крок між чанками дорівнює C − O, а кількість чанків приблизно ceil((W − O) / (C − O)). Наприклад, для анотації у 300 слів при C = 60: без перекриття вийде 5 чанків, при O = 10 (наш варіант) 6 чанків, при O = 30 уже 9. Отже, чим більше перекриття, тим більше чанків, векторів і витрат на зберігання та ембеддинг. Покриття тексту при цьому не зменшується: fixed-size охоплює весь текст за будь-якого O < C, і перекриття лише збільшує надмірність (частка повторюваного тексту приблизно O / C, у нас близько 17%). Більший overlap зберігає контекст на межах чанків і зменшує ризик втратити фразу, розрізану посередині. Проте занадто велике значення призводить до майже однакових сусідніх чанків, які дублюють одне одного у видачі пошуку. Тому перекриття в межах 10–20% від розміру чанка є розумним компромісом.


## Частина 6 — Аналіз і висновки

1. **Семантичний пошук vs пошук за ключовими словами**

Семантичний пошук добре працює, коли запит і документ описують одне й те саме різними словами. У частині 3 запит «teaching machines to recognize objects in pictures» майже не збігається за лексикою зі статтями про image classification чи object detection, але ембеддинг SPECTER2 знаходить їх за змістом, а BM25 без спільних слів нічого б не повернув. Тому семантичний підхід кращий для описових запитів, синонімів, парафраз і пошуку за схожістю. Його слабке місце: точні збіги та рідкісні токени (arXiv ID, назви категорій, імена, абревіатури, формули). Ембеддинг їх «розмиває» й повертає тематично близькі, але не ті документи, і до того ж завжди віддає top-k, навіть коли релевантного немає. У частині 4 точні умови забезпечували фільтри за метаданими (year, category). Найкраще працює гібрид.

2. **Вплив розміру чанка**

Занадто малий чанк (10–15 слів) втрачає контекст: у ньому часто немає ні підмета, ні теми, тому ембеддинг нечіткий, видача забита розрізненими фрагментами, а кількість векторів і вартість зростають. Занадто великий чанк (500+ слів) усереднює багато тем в один вектор, і конкретний факт розмивається. До того ж SPECTER2 розрахована приблизно на 512 токенів, тож хвіст довшого тексту обрізається й в ембеддингу не бере участі. Універсального оптимуму немає, він залежить від задачі: для фактологічних запитань краще 50–150 слів, для пошуку за темою чи RAG із ширшим контекстом 200–400 слів. Розмір підбирають експериментально на тестових запитах, а в метаданих зберігають номер чанка й arxiv_id, щоб підтягувати сусідні чанки.

3. **Невідповідна метрика (euclidean для нормалізованих векторів)**

Для одиничних векторів (‖a‖ = ‖b‖ = 1) маємо

    ‖a − b‖² = ‖a‖² + ‖b‖² − 2·a·b = 2 − 2·cos(a, b), тобто ‖a − b‖ = √(2·(1 − cos(a, b))).

Це строго спадна функція від cos, тож ранжування в обох метриках збігається, і індекс із euclidean повернув би ті самі top-k. Змінилася б лише шкала оцінок: замість схожості (більше означає краще, діапазон [−1, 1]) була б відстань (менше означає краще, діапазон [0, 2]), що ламає пороги на кшталт «score > 0.8» та будь-яку інтерпретацію score. Реальна проблема виникла б для ненормалізованих векторів: тоді L2 залежить від норм, і ранжування розійшлося б із косинусним. Метрику індексу не можна змінити після створення, тому її узгоджують із моделлю заздалегідь.

4. **Обмеження Pinecone Starter**

Starter дає приблизно 2 ГБ сховища, 2 млн write units і 1 млн read units на місяць, 100 namespace на індекс і лише регіон AWS us-east-1. Кількість індексів теж обмежена, а ми створили три. Також є ліміт метаданих на запис (близько 40 КБ), тому ми обрізали анотації до 500 символів і авторів до 200. Для 10 000 статей це не проблема: вектори займають ≈ 31 МБ. Для 10 млн статей самі вектори займуть ≈ 31 ГБ (10⁷ × 768 × 4 байти), тож потрібен платний тариф. Рішення: (1) тримати в метаданих мінімум, а повні тексти зберігати в окремій БД чи об'єктному сховищі; (2) рахувати ембеддинги на GPU пакетно й паралельно, завантажувати великими батчами або через bulk import; (3) розділити дані по namespace (рік, категорія) для швидших і дешевших запитів; (4) за потреби застосувати квантизацію чи розглянути self-hosted Qdrant; (5) додати гібридний пошук (dense + BM25) для точних запитів.
